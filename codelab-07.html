1

Inicio · entender el recorrido de una respuesta

Una API es una interfaz para pedir datos a otro programa. REST organiza esos datos como recursos accesibles por direcciones. Un cliente es TaskFlow; el servidor responde. Un endpoint es la URL concreta de un recurso. HTTP es el protocolo de la petición y la respuesta; GET significa consultar sin enviar una nueva tarea.

Usaremos JSONPlaceholder, una API pública de datos de prueba. Abre /todos/1 en el navegador. La respuesta tiene esta forma:

{
  "userId": 1,
  "id": 1,
  "title": "delectus aut autem",
  "completed": false
}
JSONFormato de texto para intercambiar datos. Las llaves forman un objeto; una respuesta de /todos contiene una lista de objetos entre corchetes.
Código HTTPEl servidor devuelve un número de estado. 200 indica que esta consulta se atendió correctamente. Un fallo de conexión puede ocurrir antes de recibir un código.
Future<T>Promesa de que más tarde llegará un valor de tipo T o un error. La red no responde de forma instantánea.
async / awaitasync permite esperar dentro de una función; await pausa esa función hasta obtener el resultado, sin bloquear toda la interfaz.
fromJson()Convierte un Map<String, dynamic> recibido en un objeto Task con tipos conocidos.

Comparación con la sesión 6: Task tenía seis campos. Esta API solo entrega cuatro: completed corresponde a isCompleted; description y priority no existen y recibirán valores explícitos de ejemplo. Esos valores no vienen del servidor. Más adelante, una API propia podrá entregar los seis campos.

Desarrollo B · adaptar el modelo sin perder la sesión anterior

Abre lib/features/tasks/domain/task.dart y reemplaza todo el archivo por este bloque. Mantiene las seis propiedades y copyWith de la sesión 6. Solo cambia fromJson para reconocer tanto el nombre local isCompleted como el nombre remoto completed.

class Task {
  const Task({
    required this.id,
    required this.title,
    required this.description,
    required this.priority,
    required this.isCompleted,
    required this.userId,
  });

  final int id;
  final String title;
  final String description;
  final String priority;
  final bool isCompleted;
  final int userId;

  Task copyWith({bool? isCompleted}) {
    return Task(
      id: id,
      title: title,
      description: description,
      priority: priority,
      isCompleted: isCompleted ?? this.isCompleted,
      userId: userId,
    );
  }

  factory Task.fromJson(Map<String, dynamic> json) {
    return Task(
      id: json['id'] as int,
      title: json['title'] as String,
      description: json['description'] as String? ?? 'Sin descripción (API)',
      priority: json['priority'] as String? ?? 'Sin prioridad (API)',
      isCompleted: (json['isCompleted'] ?? json['completed']) as bool,
      userId: json['userId'] as int,
    );
  }
}
Cómo leer la conversión: as int comprueba el tipo de id; String? permite que un campo no exista. ?? usa el valor de la derecha cuando el de la izquierda es null. Si el servidor cambia un tipo obligatorio, la conversión fallará; en la sesión 8 mostraremos ese error de forma más útil.

Desarrollo C · crear TaskApiService

Crea lib/features/tasks/data/task_api_service.dart y pega el archivo completo. El Service conoce la URL, el método HTTP y el formato de la respuesta. La pantalla no debe llamar a Dio directamente. El parámetro userId=1 limita los resultados a un usuario para que la práctica sea fácil de comprobar.

import 'package:dio/dio.dart';
import 'package:flutter/foundation.dart';

import '../domain/task.dart';

class TaskApiService {
  static const int userId = 1;

  TaskApiService()
      : _dio = Dio(
          BaseOptions(
            baseUrl: 'https://jsonplaceholder.typicode.com',
            connectTimeout: const Duration(seconds: 10),
            receiveTimeout: const Duration(seconds: 10),
          ),
        );

  final Dio _dio;

  Future<List<Task>> getTasks() async {
    final response = await _dio.get<List<dynamic>>(
      '/todos',
      queryParameters: {'userId': userId},
    );

    debugPrint('GET /todos?userId=$userId → HTTP ${response.statusCode}');
    final rows = response.data;
    if (rows == null) {
      throw const FormatException('La respuesta no contiene una lista.');
    }

    return rows.map((row) {
      final json = Map<String, dynamic>.from(row as Map);
      return Task.fromJson(json);
    }).toList();
  }
}

Dio convierte la respuesta JSON en datos Dart; response.data contiene la lista y response.statusCode contiene el estado HTTP. Map.from prepara cada objeto para Task.fromJson. En la configuración normal de Dio, un HTTP no exitoso produce una DioException; por eso el mensaje de consola 200 aparece cuando la respuesta se recibe con éxito.

Punto de control: aún no se verá una lista remota: el Service existe, pero todavía no está conectado al Repository y al ViewModel.

Ahora abre lib/features/tasks/data/local_task_repository.dart. Conserva tus cinco objetos Task(...) y el método save; reemplaza solo el método getTasks anterior por estas dos líneas. El archivo local debe compilar aunque la app use el repositorio remoto.

Crea lib/features/tasks/data/remote_task_repository.dart con este archivo completo. getTasks pide la lista al Service y guarda una copia en memoria. save solo cambia esa copia; JSONPlaceholder no guarda cambios permanentes y el CRUD remoto se estudiará en la sesión 10.

import '../domain/task.dart';
import 'task_api_service.dart';
import 'task_repository.dart';

class RemoteTaskRepository implements TaskRepository {
  RemoteTaskRepository(this._apiService);

  final TaskApiService _apiService;
  List<Task> _tasks = [];

  @override
  Future<List<Task>> getTasks() async {
    _tasks = await _apiService.getTasks();
    return List.unmodifiable(_tasks);
  }

  @override
  void save(Task task) {
    final index = _tasks.indexWhere((item) => item.id == task.id);
    if (index == -1) return;
    _tasks[index] = task;
  }
}
Continuidad: LocalTaskRepository conserva tus tareas de la sesión 6; RemoteTaskRepository es la nueva implementación del mismo contrato. Cambiar la fuente de datos requerirá cambiar una sola construcción en main.dart. Al recargar la API, los cambios hechos con save volverán al valor remoto original.

Desarrollo E · esperar la respuesta en el ViewModel

Reemplaza todo lib/features/tasks/presentation/tasks_view_model.dart. El ViewModel sigue siendo el puente entre datos y pantalla. loadTasks espera la red y avisa a Provider cuando termina. Una señal sencilla de carga y error evita que la pantalla quede en blanco; en la sesión 8 ampliarás estos estados y agregarás reintento.

import 'package:flutter/foundation.dart';

import '../data/task_repository.dart';
import '../domain/task.dart';

class TasksViewModel extends ChangeNotifier {
  TasksViewModel(this._repository);

  final TaskRepository _repository;
  List<Task> _tasks = [];
  bool isLoading = false;
  String? errorMessage;

  List<Task> get tasks => List.unmodifiable(_tasks);

  Future<void> loadTasks() async {
    isLoading = true;
    errorMessage = null;
    notifyListeners();

    try {
      _tasks = await _repository.getTasks();
    } catch (error) {
      errorMessage = 'No se pudieron cargar las tareas.';
      debugPrint('Error al cargar tareas: $error');
    } finally {
      isLoading = false;
      notifyListeners();
    }
  }

  Task? findTask(int? id) {
    if (id == null) return null;
    for (final task in _tasks) {
      if (task.id == id) return task;
    }
    return null;
  }

  void toggleCompleted(int id) {
    final current = findTask(id);
    if (current == null) return;

    final updated = current.copyWith(isCompleted: !current.isCompleted);
    _repository.save(updated);
    _tasks = [
      for (final task in _tasks) if (task.id == id) updated else task,
    ];
    notifyListeners();
  }
}

Por qué cambió toggleCompleted: antes llamaba otra vez a getTasks() después de save. Ahora esa llamada volvería a consultar el servidor y perdería el cambio local. El método actualiza la lista en memoria y notifica a las dos pantallas. try/catch/finally permite cerrar la carga tanto si hay datos como si hay un fallo.

Desarrollo F · mostrar los datos y conectar la app

Reemplaza todo lib/features/tasks/presentation/task_list_screen.dart. El listado usa el mismo context.watch de la sesión 6, así que Provider reconstruye la vista cuando cambia el ViewModel. La navegación por id se conserva.

import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';
import 'package:provider/provider.dart';

import 'tasks_view_model.dart';

class TaskListScreen extends StatelessWidget {
  const TaskListScreen({super.key});

  @override
  Widget build(BuildContext context) {
    final viewModel = context.watch<TasksViewModel>();

    return Scaffold(
      appBar: AppBar(title: const Text('Mis tareas')),
      body: viewModel.isLoading
          ? const Center(child: CircularProgressIndicator())
          : viewModel.errorMessage != null
              ? Center(child: Text(viewModel.errorMessage!))
              : viewModel.tasks.isEmpty
                  ? const Center(child: Text('No hay tareas para mostrar.'))
                  : ListView.builder(
                      padding: const EdgeInsets.all(16),
                      itemCount: viewModel.tasks.length,
                      itemBuilder: (context, index) {
                        final task = viewModel.tasks[index];
                        return Card(
                          child: ListTile(
                            leading: Icon(
                              task.isCompleted
                                  ? Icons.check_circle
                                  : Icons.radio_button_unchecked,
                            ),
                            title: Text(task.title),
                            subtitle: Text('Prioridad: ${task.priority}'),
                            trailing: const Icon(Icons.chevron_right),
                            onTap: () => context.push('/task/${task.id}'),
                          ),
                        );
                      },
                    ),
    );
  }
}

Por último, reemplaza todo lib/main.dart por este bloque. ..loadTasks() crea el ViewModel y llama a su método de carga antes de mostrar la app. taskflow_app.dart y task_detail_screen.dart de la sesión 6 no necesitan cambios.

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import 'app/taskflow_app.dart';
import 'features/tasks/data/remote_task_repository.dart';
import 'features/tasks/data/task_api_service.dart';
import 'features/tasks/data/task_repository.dart';
import 'features/tasks/presentation/tasks_view_model.dart';

void main() {
  final TaskRepository repository = RemoteTaskRepository(TaskApiService());

  runApp(
    ChangeNotifierProvider<TasksViewModel>(
      create: (_) => TasksViewModel(repository)..loadTasks(),
      child: const TaskFlowApp(),
    ),
  );
}

Recorrido completo: main.dart construye las dependencias → el ViewModel pide getTasks() → el Repository llama al Service → Dio hace GET → fromJson() crea objetos Task → notifyListeners() actualiza la lista → la ruta abre el detalle por id.
