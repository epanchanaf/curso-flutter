DOCUMENTO CANÓNICO DEL CURSO

Reglas para producir los contenidos de las semanas siguientes.

Estas especificaciones deben aplicarse cada vez que se cree o amplíe una sesión, un codelab, una práctica autónoma o una sección del sitio.

CONTEXTO FIJO

AudienciaEstudiantes de quinto nivel de una carrera tecnológica.
Duración7 semanas · 14 sesiones · 35 horas: una sesión de 3 h y otra de 2 h por semana. Formularios se integra con CRUD; calidad se integra con APK, demostración y evaluación para conservar todos los contenidos.
ResultadoTaskFlow: app Flutter Android conectada a una API REST.
ArquitecturaMVVM + Repository + ApiService, organizada por funcionalidades.
01

Estructura obligatoria de cada sesión

Cada sesión debe presentar una meta observable y organizarse explícitamente en los tres momentos de clase:

Inicio

Activación de saberes previos, contexto del problema y objetivo de aprendizaje. Incluir duración estimada.

Desarrollo

Explicación conceptual detallada, ejemplo guiado y práctica acompañada. No asumir que el estudiante conoce el término técnico.

Cierre

Comprobación funcional, síntesis, evidencia requerida y conexión con la siguiente sesión.

02

Nivel de detalle pedagógico

  • Definir cada concepto nuevo en lenguaje claro antes de usarlo.
  • Explicar qué problema resuelve, dónde se utiliza y qué ocurre si se usa incorrectamente.
  • Incluir criterios de comprobación: “qué debe verse”, “qué debe cambiar” o “qué debe ejecutar”.
  • Incorporar errores frecuentes y una orientación inicial para diagnosticarlos.
  • Usar TaskFlow como hilo conductor para que los conceptos no aparezcan aislados.
03

Trabajo integrador autónomo

Cada sesión debe incluir una propuesta de trabajo autónomo que extienda TaskFlow según el tema revisado. No puede ser un reto genérico ni repetir exactamente el ejemplo guiado.

FORMATO REQUERIDO

Aplicar: conceptos vistos en la sesión.

Avance: mejora funcional concreta dentro de la app final.

Evidencia: comportamiento observable, captura, prueba o artefacto.

Versionado: mensaje de commit sugerido y push a GitHub.

Ejemplo: si se estudian Column y Row, el trabajo autónomo debe construir una sección real de TaskFlow —por ejemplo, la tarjeta de tareas pendientes— usando esos widgets; no una pantalla de ejemplo sin relación con el proyecto.

04

Git y GitHub

El ejemplo guiado sirve para aprender y no constituye la evidencia a versionar. Al finalizar exclusivamente el trabajo autónomo de cada sesión, el estudiante debe comprobar el avance y ejecutar:

git status
git add .
git commit -m "mensaje sugerido para el avance autónomo"
git push origin main

La especificación de cada sesión debe proporcionar un mensaje de commit descriptivo. El historial de GitHub es la evidencia de progreso del trabajo integrador.

05

Formato de codelabs

Cuando una sesión incluya programación, generar un codelab asociado. Debe contener precondiciones, pasos numerados, explicación antes y después de cada bloque, resultado esperado, retos autónomos y errores frecuentes.

  • Los ejemplos Dart se presentan en bloques con resaltado de sintaxis Dart.
  • Los comandos se marcan como bloques de terminal/Shell.
  • Todo bloque de código debe incluir el botón Copiar.
  • El reto autónomo debe indicar la mejora de TaskFlow, la evidencia y el commit/push correspondiente.

07

Entrega y publicación del sitio

Los contenidos se mantienen en una web estática, responsive y accesible, preparada para GitHub Pages. Toda nueva página debe conservar navegación hacia plan, codelabs, proyecto y estas especificaciones.
